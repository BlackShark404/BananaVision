# BananaVision Data Dictionary (Detailed)

Current application schema at Alembic revision `0010_notification_read_receipts`, derived from
`docs/bananavision_schema_current.sql` and checked against the SQLAlchemy models. The
schema contains **25 application tables**, 7 PostgreSQL enum types and 20 foreign-key
relationships. The technical `alembic_version` table is excluded.

This companion version adds **Description** and **Constraints** columns and separates
key/reference details into **Key** and **References**. It keeps the database-level
PostgreSQL types, so enum columns show `ACTIVESTATUSENUM` rather than the Python class
`ActiveStatusEnum`.

## Notation

- `Auto-increment` — backed by a PostgreSQL sequence (`SERIAL`).
- `Application-generated (...)` — generated by the backend/ORM before insert.
- `Application default: ...` — supplied by the backend/ORM when the caller omits a value.
- Plain value — actual PostgreSQL server default.
- `—` — no default, no key, no reference, or no additional constraint.
- `PK` — primary key; `FK` — foreign key; `FK (Unique)` — unique foreign key.
- `References` uses `TABLE(COLUMN)` notation.

## Enum types

| PostgreSQL enum | Model enum | Database labels | Application values |
| --- | --- | --- | --- |
| `ACTIVESTATUSENUM` | `ActiveStatusEnum` | `ACTIVE`, `INACTIVE` | Active, Inactive |
| `CULTIVARENUM` | `CultivarEnum` | `LAKATAN`, `LATUNDAN`, `CARDABA` | Lakatan, Latundan, Cardaba |
| `DEVICESTATUSENUM` | `DeviceStatusEnum` | `ONLINE`, `OFFLINE` | Online, Offline |
| `INTAKESTATUSENUM` | `IntakeStatusEnum` | `ACTIVE`, `DEPLETED` | Active, Depleted |
| `INVENTORYSTATUSENUM` | `InventoryStatusEnum` | `IN_STOCK`, `SOLD`, `FOR_PROCESSING`, `SPOILED` | In Stock, Sold, For Processing, Spoiled |
| `RIPENESSENUM` | `RipenessEnum` | `UNRIPE`, `SEMI_RIPE`, `RIPE`, `OVERRIPE` | Unripe, Semi Ripe, Ripe, Overripe |
| `TREATMENTENUM` | `TreatmentEnum` | `Natural`, `Ethephon` | Natural, Ethephon |

SQLAlchemy stores enum member names by default, so most PostgreSQL labels are uppercase
even though the API returns title-case values. `TreatmentEnum` uses `values_callable`, so
its database labels are the same as its application values.

## Normalization notes

- Camera configuration is normalized into one `DEVICE` row per saved slot.
- Operator scan totals are derived from `SCAN`; they are not stored in `OPERATOR_PROFILE`.
- `SCAN_CLASSIFICATION` and `SCAN_ORIGINAL_AI_RESULT` are 1:1 detail tables keyed by a
  unique `SCAN_ID`.
- Notification content is stored once in `APP_NOTIFICATION`; per-account read state is
  normalized into `APP_NOTIFICATION_READ` rather than a shared flag on the notification.
- Historical snapshots, audit JSON and engineered features are intentional controlled
  denormalization for auditability and reproducibility.

## ORM relationship coverage

Every foreign-key relationship in the schema has a corresponding SQLAlchemy ORM
`relationship()` declaration enabling bidirectional navigation:

- **`SCAN`** navigates to its classification, status logs, original AI result, detections,
  images, notes, print jobs and events via eager-loaded or on-demand relationships.
- **`SCAN_LABEL_PRINT_JOB`** links to its parent scan (`scan`) and the requesting user
  account (`owner`).
- **`SCAN_EVENT`** links to its parent scan (`scan`).
- **`SUPPLIER`** ↔ **`DELIVERY_INTAKE`** is fully bidirectional (`intakes` / `supplier`).
- **`SCAN_LABEL_PRINT_JOB.print_jobs`** and **`SCAN_EVENT.events`** on the `Scan` model
  use `lazy="raise"` so they are not eagerly loaded on every scan query.
- **`DEVICE`** ↔ **`SCAN_DETECTION`** and **`SCAN_IMAGE`** provide reverse links (`detections` /
  `images` with `lazy="raise"`) and direct references (`device` with `lazy="selectin"` on detection/image).

Five models intentionally have no ORM relationships: `SENSOR_READING` (standalone
time-series), `MAINTENANCE_STATE` (system singleton), `SCAN_BROWSE_SNAPSHOT` (ephemeral, no FK),
`SCAN_MUTATION` (audit immutability, no FK) and `SCAN_TOMBSTONE` (deleted-scan evidence, no FK).

For the complete ORM relationship map with loading strategies, see `docs/schema_tables.md`.
For the exact PostgreSQL DDL and constraint names, see `docs/bananavision_schema_current.sql`.
