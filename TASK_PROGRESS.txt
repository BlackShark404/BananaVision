BRANCH main; prior checkpoint archived below.

DONE / EVIDENCE
- Fixed Camera Calibration Modal (frontend/src/components/CameraCalibrationModal.tsx):

  1. Position dropdown showing camera IDs instead of labels:
     - Root cause: `labels` state was populated from `cam.camera_id` (e.g. "CAM-001", "CAM-003")
       instead of `cam.label` (e.g. "Top", "Left", "Right", "Rear").
     - The backend GET /api/v1/cameras already returns a `label` field sourced from
       settings.camera_labels (config.py default: ["Top", "Left", "Right", "Rear"]).
     - Fix: changed `data.map(cam => cam.camera_id)` → `data.map(cam => cam.label)` for both
       the `labels` state and the `mapping` keys. Dropdown now shows physical positions.

  2. Position swap on selection:
     - Previously, selecting a position already assigned to another camera created duplicate
       mappings, which was caught at save time with a toast error.
     - Fix: `onValueChange` handler now performs an atomic swap — if Camera A has "Top" and
       Camera B has "Left", reassigning Camera A to "Left" automatically gives Camera B "Top".

  3. "Operation ID already used" error on re-save:
     - Root cause: `operationId.current` was never reset after a save. The `??=` assignment
       reused the consumed UUID on the next attempt, and the backend rejected it (409).
     - Fix: added `operationId.current = null` in the `finally` block so each save
       generates a fresh UUID.

  4. Modal not closing after successful save with offline cameras:
     - Root cause: modal only closed when `application_status === "applied"`. With 3 of 4
       cameras physically offline, status was never "applied", so the modal stayed open
       showing an error even though the mapping was persisted correctly.
     - Fix: `setOpen(false)` is now called unconditionally on successful save. Toast
       differentiates: green success when fully applied, yellow warning with detail when
       some cameras couldn't initialize.
